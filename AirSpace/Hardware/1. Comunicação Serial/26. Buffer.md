Um **buffer** é uma **região de memória temporária** usada para armazenar dados que estão **em trânsito** entre dois dispositivos ou processos.

No caso da comunicação serial (como RS-232, DF1, UART etc.), tanto o **transmissor (TX)** quanto o **receptor (RX)** possuem seus próprios buffers.

- O **TX buffer** guarda os bytes **que serão enviados**.
    
- O **RX buffer** guarda os bytes **que já chegaram**, mas ainda **não foram processados** pelo programa.
    

---

## 📥 Quando o buffer está “cheio”

Dizemos que o buffer está **cheio** quando ele **alcança sua capacidade máxima de armazenamento** e **não há mais espaço** para novos bytes.

👉 Exemplo:

Se o receptor (CLP ou PC) tem um **buffer RX de 16 bytes**,  
e o transmissor envia **mais de 16 bytes antes do receptor ler os anteriores**,  
o **17º byte se perde** — porque **não há espaço para guardá-lo**.

---

## 💡 Situação típica na prática

Imagine o CLP enviando 64 bytes para o PC:

1. O CLP envia os bytes pela UART (TX).
    
2. O PC recebe pela UART (RX).
    
3. Se o PC estiver **lendo devagar** (talvez o software esteja ocupado),  
    os bytes começam a **acumular** no **RX buffer**.
    
4. Quando o buffer atinge o limite → **“buffer cheio”**.
    

O hardware, então, **sinaliza isso** de duas formas:

- via **CTS (Clear To Send)** → desativa o sinal, pedindo para o transmissor _pausar_.
    
- ou via **interrupção/flag de overflow**, se o sistema não usa controle de fluxo físico.
    

---

## 🧠 Ligando isso ao DF1 e ao RTS/CTS

Lembra do trecho do protocolo DF1?

> “if message header is different from last and sink is not full”  
> “try to send message to sink”

Aqui o _sink_ é o **buffer de recepção**.  
Então:

- **sink is not full** → o receptor ainda tem espaço.
    
- **sink is full** → o receptor está sobrecarregado e precisa rejeitar o novo pacote.
    

E quando isso ocorre, o transmissor pode:

- **Esperar o CTS** voltar a ativo (hardware controlado), ou
    
- **Receber um NAK**, indicando que a mensagem não foi aceita.
    

---

## 🔄 Analogia simples

Pense no **buffer** como um **balde**:

- O **transmissor** joga água (dados).
    
- O **receptor** retira a água (lê os dados).
    
- Se o receptor for lento e o balde encher → o transmissor precisa parar,  
    ou a água (dados) **transborda** — **perda de bytes**.
    

---

## 📊 Tipos de buffers em UART

|Tipo|Tamanho típico|Responsável|Descrição|
|---|---|---|---|
|**TX buffer**|1 a 64 bytes|UART transmissora|Armazena dados antes do envio|
|**RX buffer**|1 a 64 bytes|UART receptora|Armazena dados recebidos até o programa ler|
|**Software buffer**|128+ bytes|Driver UART|Estende a capacidade da UART via RAM|
> 🔹 **A aplicação sabe o estado do buffer e pode decidir o que fazer (ACK/NAK, repetir, etc.).**  
> 🔹 **O hardware controla fisicamente o fluxo via CTS/RTS, garantindo que os bytes não se percam.**

Então a aplicação **não precisa manipular diretamente o pino CTS** — ela apenas é **notificada** (ou depende da UART) que o envio foi pausado ou liberado.
